# HTTP/SSE + session_id 前后端联调清单

## 文档目的

本文档用于串联以下两部分改造后的联调验证：

- 后端：`D:\learn\langChainDemo`
- 前端：`D:\Demo\ai-japanese-learning`

目标是确认 `HTTP/SSE + session_id` 聊天链路在本地、开发者工具、真机环境下都能稳定工作。

本次只输出联调清单，不包含代码改动。

---

## 一、联调目标

联调完成后，应确认以下结果全部成立：

1. 前端发送聊天消息时，能通过 `POST /chat/stream` 成功请求后端。
2. 后端返回的是标准 `SSE` 事件流，而不是一次性整包文本。
3. 前端能持续收到并解析 `chunk` 事件。
4. 前端能正确处理 `done` 事件并结束流式状态。
5. 前端能正确处理 `error` 事件并展示失败状态。
6. 同一 `session_id` 可以继承上下文。
7. 不同 `session_id` 之间不会串上下文。

---

## 二、联调前置条件

### 2.1 后端前置条件

后端应先满足以下条件：

1. 已提供 `POST /chat/stream`
2. 请求体接收：

```json
{
  "message": "你好",
  "session_id": "assistant_xxx"
}
```

3. 响应为 `text/event-stream`
4. 事件至少包含：

- `chunk`
- `done`
- `error`

5. 后端 `session_id` 已实现真实隔离

### 2.2 前端前置条件

前端应先满足以下条件：

1. 聊天链路已切到 `HTTP/SSE`
2. 当前 active conversation 会把自己的 `sessionId` 带到请求体
3. 前端已具备 `SSE` 文本解析能力
4. `stores/assistant.js` 已继续沿用当前多会话结构

### 2.3 环境前置条件

联调前建议先确认：

1. 前端请求地址与后端实际启动地址一致
2. 微信开发者工具已允许访问本地或局域网服务
3. 如果使用手机真机，前端请求地址应改成可访问的局域网 IP，而不是 `127.0.0.1`

---

## 三、推荐联调顺序

建议按下面顺序联调：

1. 后端裸接口联调
2. 前端协议解析联调
3. 单会话联调
4. 多会话联调
5. 异常场景联调
6. 真机联调

不要一开始就直接在真机上查所有问题，否则定位成本会很高。

---

## 四、后端裸接口联调

目标：

- 先不经过前端，单独确认后端事件流格式正确

### 4.1 验证请求是否可达

确认以下接口可以访问：

- `POST /chat/stream`

### 4.2 验证响应头

应确认响应头至少包含：

- `Content-Type: text/event-stream`
- `Cache-Control: no-cache`

### 4.3 验证事件格式

预期应看到类似结果：

```text
event: chunk
data: {"text":"你"}

event: chunk
data: {"text":"好"}

event: done
data: {"reply":"你好","suggestion":"..."}

```

重点确认：

1. 每个事件之间有空行分隔
2. `data:` 是合法 JSON
3. 最终一定有 `done`
4. 出错时是 `error`，不是直接断连接

### 4.4 验证会话隔离

建议用两个不同 `session_id` 分别测试：

- `session_a`
- `session_b`

应确认：

1. `session_a` 第二轮提问可承接第一轮上下文
2. `session_b` 首轮提问不会带出 `session_a` 的内容

---

## 五、前端协议解析联调

目标：

- 确认前端能把原始 HTTP chunk 正确解析成 `SSE` 事件

### 5.1 原始文本接收验证

前端应先确认能拿到原始流式文本 chunk，而不是一次性拿到完整全文。

如果前端只能在最后一次性拿到所有内容，说明当前平台或请求实现没有真正流式工作。

### 5.2 buffer 拆帧验证

前端应确认以下逻辑都正确：

1. 原始 chunk 可能是不完整半帧
2. 多个事件可能粘在一个 chunk 里
3. 需要先进入 buffer 再按 `\n\n` 切帧

### 5.3 事件解析验证

前端应确认以下解析结果都正确：

1. `event: chunk` 被识别为文本增量事件
2. `event: done` 被识别为结束事件
3. `event: error` 被识别为失败事件
4. `data:` 中的 JSON 能被正常解析

---

## 六、单会话联调

目标：

- 确认“一个会话连续聊天”的完整链路可用

### 6.1 首轮消息

验证点：

1. 用户发送一条消息
2. assistant 占位气泡出现
3. assistant 内容逐步增长
4. 收到 `done` 后结束流式
5. suggestion 正常更新

### 6.2 第二轮消息

验证点：

1. 同一会话继续发第二条消息
2. 后端仍收到同一个 `session_id`
3. 回复内容能体现上下文延续

### 6.3 刷新后恢复

如果前端有本地存储恢复逻辑，应确认：

1. 刷新页面后仍能回到上一次 active conversation
2. 再次发送消息时仍沿用该 conversation 的 `sessionId`

---

## 七、多会话联调

目标：

- 确认会话抽屉、新建会话、历史切换都与 `session_id` 隔离一致

### 7.1 新建会话

验证点：

1. 点击“新建对话”
2. 前端生成新的 conversation
3. 新 conversation 使用新的 `sessionId`
4. 发送首条消息时不会继承旧会话上下文

### 7.2 切换历史会话

验证点：

1. 打开对话抽屉
2. 切换到旧会话
3. 消息列表切回旧内容
4. 再发送消息时，请求体携带的是旧会话的 `sessionId`
5. 后端回复能承接旧会话上下文

### 7.3 来回切换

建议至少验证：

1. 会话 A 聊两轮
2. 新建会话 B 聊一轮
3. 切回会话 A 再聊一轮

预期：

- A 和 B 的上下文彼此独立

---

## 八、异常场景联调

目标：

- 确认失败路径可控，不再只有模糊的“连接失败”

### 8.1 后端主动返回 `error`

验证点：

1. 前端能识别 `error` 事件
2. 页面结束流式状态
3. 输入框按现有产品逻辑回填
4. 给出合理错误提示

### 8.2 后端异常中断

验证点：

1. 如果响应流被中途断开
2. 前端是否能识别为异常结束
3. assistant 占位消息是否能落到明确失败态

### 8.3 非法请求参数

至少验证：

1. `message` 为空
2. `session_id` 缺失
3. `session_id` 格式异常

预期：

- 后端有明确错误响应
- 前端不会卡死在 `isStreaming`

---

## 九、开发者工具联调清单

目标：

- 确认微信开发者工具里链路可用

建议确认：

1. Network 面板能看到 `POST /chat/stream`
2. 请求体里有正确的 `message` 和 `session_id`
3. 响应不是整包 JSON，而是流式文本
4. 页面消息气泡能逐步增长
5. 切换会话后，请求体里的 `session_id` 会变化

如果开发者工具里能通，但真机不通，优先怀疑：

1. 请求地址仍是 `127.0.0.1`
2. 真机网络权限或白名单限制
3. 局域网 IP 与服务监听地址不一致

---

## 十、真机联调清单

目标：

- 确认真机环境与开发者工具行为一致

建议确认：

1. 请求地址已改成电脑局域网 IP
2. 手机与电脑在同一局域网
3. 后端服务监听地址不是只绑定 `127.0.0.1`
4. 真机发送后，能持续收到流式文本
5. 切换历史会话后，真机也不会串上下文

真机最重要的检查点：

- 是否真的“边返回边显示”

因为有些环境会在开发者工具表现正常，但真机侧流式能力不同。

---

## 十一、推荐日志观察点

### 11.1 后端日志

建议观察：

1. 接口是否收到请求
2. 收到的 `session_id` 是否符合预期
3. 每轮是否持续输出 chunk
4. 结束时是否发送 `done`
5. 出错时是否发送 `error`

### 11.2 前端日志

建议观察：

1. 请求开始日志
2. 原始 chunk 接收日志
3. `SSE` 解析日志
4. `chunk` 事件累计长度
5. `done` 事件完成日志
6. `error` 事件失败日志

如果保留调试日志，建议语义从 socket 风格调整成 stream 风格：

- `request-start`
- `raw-chunk`
- `sse-frame`
- `chunk`
- `done`
- `error`
- `finish`

---

## 十二、问题定位优先级

联调中如果出现问题，建议按以下顺序定位：

1. 后端接口是否真的返回标准 `SSE`
2. 前端是否真的拿到了流式 HTTP chunk
3. 前端 buffer 拆帧是否正确
4. `event/data` 解析是否正确
5. `session_id` 是否在切换会话时正确变化
6. 真机环境网络是否可达

不要一开始就怀疑 LangChain 本身，先确认协议链路和 session 隔离。

---

## 十三、联调完成验收标准

联调完成后，应满足以下标准：

1. 前端发送一条消息后，assistant 回复可流式增长
2. 流结束由后端 `done` 显式通知
3. 出错由后端 `error` 显式通知
4. 新建会话会生成新的 `sessionId`
5. 切换历史会话会使用对应旧 `sessionId`
6. 会话 A 与会话 B 上下文完全隔离
7. 开发者工具和真机环境结果一致或可解释

---

## 十四、结论

这次联调的核心不是单纯“接口通不通”，而是同时确认这三件事：

1. 流式协议是否成立
2. `session_id` 隔离是否成立
3. 小程序端是否真的能稳定消费流式响应

只要这三件事同时成立，`HTTP/SSE + session_id` 这条链路才算真正可用。
